# Panerelay RFCs

RFCs define significant Panerelay protocol, architecture, security, and product decisions before implementation makes them expensive to change.

## Statuses

- `Draft`: under active design and open to substantial changes
- `Accepted`: approved for implementation
- `Implemented`: accepted and represented by released code
- `Rejected`: considered but not selected
- `Superseded`: replaced by another RFC

## File naming

Use a four-digit sequence followed by a concise kebab-case title:

```text
0001-extension-connection-and-agent-interoperability.md
```

## Required metadata

Every RFC starts with:

```text
RFC: 0000
Title: Short title
Status: Draft
Authors: GitHub handles or names
Created: YYYY-MM-DD
Updated: YYYY-MM-DD
```

## Recommended sections

1. Summary
2. Motivation
3. Goals and non-goals
4. Terminology
5. Proposed design
6. Protocol and data model
7. Security and privacy
8. Compatibility and migration
9. Alternatives considered
10. Delivery plan
11. Acceptance criteria
12. Open questions

RFCs should distinguish decisions from open questions, describe rejected alternatives fairly, and include enough detail for an independent implementation.
